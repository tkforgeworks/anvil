# T-058 report: shared editor, list and widget framework (area `fw`)

Baseline `a0823e2` on `review/1.0.0-baseline`. Read-only review; `fvm flutter analyze` → `No issues found!`.

## 1. Summary

The framework is mostly in good shape. Most files are small and do one job, the editor save model is clean, and only one file goes over 500 lines (`lists/record_list_page.dart`, 521). The problems are about where code lives and what the framework fails to offer:

1. **The framework is missing the parts the six editors keep rewriting.** Six editor scaffolds, six load-failure views, six overviews, four Duplicate flows, three notices, five sets of reorder/remove row buttons and six create dialogs are each written separately under `domains/`. This is the largest source of duplicated code in the app.
2. **Dependency direction.** List adapters reach their repository through the page's `WidgetRef`. Shared vocabulary sits in the wrong files: the error-to-message helpers, `findDirtyEditor`, `clockProvider`, `formatDeletedAt` and the `ShellDomain` mappings live in `editor/` or `lists/` files that 19 other files import. This creates two import cycles (editor↔shell, lists↔export).
3. **Complexity hot spots.** `RecordListPage` (521 lines, build cc 14), `exit_prompt.dart` (two dialogs, cc 15), `CustomFieldsPanel._field` (cc 19) and `EditHeader.build` (140 lines).

## 3. Proposed tickets

Every ticket keeps the existing `ValueKey`s, so the widget tests prove the behaviour is unchanged. Every ticket's done-checks start with:
`fvm dart format --set-exit-if-changed .` → exit 0; `fvm flutter analyze` → `No issues found!`; `fvm flutter test test packages/anvil_core/test` → `All tests passed!`. Only extra checks are listed below.

**fw-T1 — Add a guard test that stops files and functions growing past the agreed limits.** Closes the guard-test item (no findings). Scope: `pubspec.yaml` (root `dev_dependencies: analyzer`), `pubspec.lock` (the lockfile change is part of the work), new `test/architecture/code_metrics.dart` (~200: the AST visitor from the metrics tool), `test/architecture/code_metrics_test.dart` (~90), `test/architecture/code_metrics_allowlist.dart` (~120 of `const` data).
- *Measures*, over `lib/` and `packages/anvil_core/lib/`: file lines > 500; cyclomatic complexity > 15 per function, method or closure; nesting > 4; `build()` > 100 lines; more than one public type per file.
- *Exemptions*: path patterns (`db/migrations/`, `project/templates/`) and named entries with a reason string.
- *Allow-list*: keys `path` or `path#Type.method` (never line numbers), each with today's value as its ceiling.
- *Two failure modes*: (a) an entry goes above its ceiling, or a new violator appears; (b) an entry is now at or under the threshold, so the test fails with "remove stale entry". Each refactor ticket must therefore shrink the list in the same PR.
- *A self-test* parses fixed snippets, as the colour test does.
- *Ports needed*: the metrics tool uses analyzer 14.x APIs (`namePart`, `BlockClassBody`, `primaryConstructor`), but the workspace resolves analyzer 13.3.0 (`pubspec.lock:12-19`). Pin the version pub already resolves and port the visitor. Also fix two gaps: top-level variable initialisers (provider closures) are not measured today, and `lineCount` is `wc -l` + 1.
- Depends: none; land first. Size M. Risk: the analyzer version pin (low). Tests: new files only. Done-check: `fvm flutter test test/architecture` → passes; deleting one allow-list entry → the test fails naming that path.

## 7. Open questions

1. **Undo after leaving a list (F29).** Keeping a Delete/Restore Undo alive after the page goes is a **behaviour change**, separate from the pure fw-T9. The controller is `autoDispose` and dies with the page, so the Undo would have to run through the container, as `_undoDuplicate` does. Routing a single-record Undo through `LifecycleRepository.bulk*` would write `1 item restored`, not `<name> - Item restored`, changing the `save_history` rows. Should the Undo outlive the page, and with which history row?
2. **List page titles (F30).** Use 0.1.6's `Crafting Recipes` / `Character Classes`, through a `ShellDomain.pageTitle` field? This is a behaviour change.
3. **Load-failure looks (F19).** Unify on `ForgeErrorCard`, or keep both? A small visual change.
4. **Small visual variants** the shared widgets preserve through flags: overview letter spacing 0.66 vs 0.6; the Deleted chip with or without a transparent background; link underline; the `auto ` prefix and error text vs card in create dialogs; `Remove` vs `Remove assignment` tooltips. Unifying any of them removes a flag but changes pixels, and there are no golden tests to catch it.
