# T-060 report: settings, export and menu (area `sem`)

Baseline `a0823e2` on `review/1.0.0-baseline`. 25 files, 7,762 lines (`wc -l`). `fvm flutter analyze lib/app/settings lib/app/export lib/app/menu` reports `No issues found!`.

## 1. Summary

The area works and is well documented. The weak spots are a few oversized files where unrelated jobs sit together, and copied scaffolding inside settings. Plugin confinement holds: `url_launcher` is only in `menu/external_links.dart` and `package_info_plus` only in `menu/about_dialog.dart`. The Project Settings split works as CLAUDE.md describes: the buffered lists and the immediately-persisting Custom Fields tab use separate controllers in separate files. The top three problems:
1. **Menu commands are one big `switch`, not a registry.** Adding a command edits up to seven places in three files: the enum, three sets/maps, the `dispatchCommand` switch (cc 32), the menu tree in `app_menu.dart` (a 180-line `build`), and the shortcut table, which repeats every label.
2. **The settings sections repeat the same scaffolding.** The Project Settings meta sections have three copies of the same state and table code. The two settings dialogs each have their own copy of `_TabScroll`, `_SettingLabel` and the header and tab frame. Adding a meta list kind means four `switch`es in a 521-line controller.
3. **The export controller and page each do too much.** `export_controller.dart` (622 lines, 6 public types) handles selection, preview/execute with `dart:io` file writes, and template CRUD. `export_page.dart` `_form` has cc 28 over 152 lines. The export code also keeps its own copy of the ShellDomain↔ExportDomain mapping and a six-arm repository `switch`.

## 6. Discrepancies

1. The brief expected `meta_list_section.dart` to hold "one section per meta list kind". It is the shared widget kit (16 public types). The only section in it is `MetaListSection` (`:528`); rarity and derived stats have their own files.
2. Metrics line counts are one higher than `wc -l` for every file (e.g. 742 vs 741). This is a counting convention and changes no conclusion.
3. CLAUDE.md Known Gaps quotes the app-bar tooltip as `N record(s) with unsaved changes`. The source is `'$count ${count == 1 ? 'record' : 'records'} with unsaved changes'` (`shell/save_status_indicator.dart:73`). The `record(s)` wording does exist, but in the export page's dirty note (`export/export_page.dart:286`), which counts record editors only (`:81-85`).
4. CLAUDE.md says `export_key_slug.dart` is "the one key slugifier for create dialogs". That holds for create dialogs, but there is a second slugifier, `slugifyMetaKey` (`settings/project/meta_buffer.dart:196`, `_` separator, 0.1.6 parity), for Project Settings rows. Worth a CLAUDE.md line.
5. Metrics duplicates `_GeneralTab` (both settings dialogs) and `_Footer` (`project_settings_dialog.dart:190` vs `welcome/welcome_page.dart:286`) are name collisions between unrelated widgets, not copies. `_TabScroll` and `_SettingLabel` are real copies.
6. The brief's 23-entry registry, file counts (12 / 4 / 9) and "10 of 12 settings files have more than one public type" all match the source.
7. CLAUDE.md's Project Settings split (buffered lists on one Save, Custom Fields immediate) matches the source and is clean in structure: `project_settings_controller.dart:1-8` and `custom_fields_controller.dart:1-5` are separate controllers.
8. `fvm flutter analyze` printed `Got dependencies!` (it runs an implicit `pub get`). `pubspec.lock` was unchanged afterwards, so it is safe in practice but not strictly read-only.

## 7. Open questions

1. **`Project Settings (settings)` and the tooltip** (sem-F30). Both are behaviour changes in `editor/` and `shell/`. For example, let `DirtyEditor.other` omit the bracket (`kindLabel` optional) so the prompt reads `Project Settings`, and have the tooltip either count only record entries or say `N unsaved changes`. Should these be 0.2.1 behaviour tickets, separate from the refactor?
2. **Dialogs open across a project close** (sem-F31). The structural fix is to close root-navigator dialogs when the session clears, which is a behaviour change. Wanted, and in which release?
3. **Where export file writing belongs** (sem-T9). The architecture puts "files" in the core, and `export_controller.dart:470-486` writes files in the app. sem-T9 extracts an app-level `ExportFileWriter` as a pure refactor. Should a later ticket move it into `packages/anvil_core` (`ExportService.write…`)? That would change the core's public API, so it needs your call.
4. **Template save error text.** `template_dialog.dart:277` maps errors through `listErrorMessage`, which has no `SaveBlocked` case, so a blocked save shows `Failed to save template.` while `:280` reports `SaveOutcome.blocked`. Is that intended? Changing it is a behaviour change.
5. **`MetaPicker` vs `DraftPicker`.** `editor/widgets/draft_picker.dart:5-6` documents the difference. Merge them (cross-area, with a flag), or keep both?
6. **Nav commands.** sem-T3 keeps the fixed `navClasses` … `navLootTables` enum values (0.1.6 ids, `Ctrl+2`…`Ctrl+7`). A seventh domain would still need a new enum value and registry row. OK as the deliberate limit?
