## Decisions already taken (do not re-decide)
- Drafts carry no id, so the save signature is `Future<XDraft> save(String id, XDraft draft)`;
  `create` and `duplicate` return the `XRecord` (the caller needs the new id).
- `load(id)` returns the draft for any existing row, soft-deleted or not (the recycle bin may
  show it); `save` requires `deleted_at IS NULL` and throws `RecordNotFound` otherwise.
- `softDelete`, `restore`, `hardDelete`, `duplicate` throw `RecordNotFound` for an unknown id
  (0.1.6 silently did nothing); each is its own `saveTransaction` with its own history row.
- The export-key uniqueness check runs in Dart before the write (`SELECT 1 FROM <table> WHERE
  export_key = ? AND id != ?`) and throws `DuplicateExportKey(key)` with the key filled in, so
  the `UNIQUE` constraint is never reached in the normal path.
- Save blockers are pure functions in the domain layer, exported from `domain.dart`:
  `List<SaveBlocker> itemSaveBlockers(ItemDraft)` in `lib/src/domain/item_save_blockers.dart`,
  `recipeSaveBlockers(RecipeDraft)` in `recipe_save_blockers.dart`,
  `lootTableSaveBlockers(LootTableDraft)` in `loot_table_save_blockers.dart`. The repository `save`
  calls the same function and throws `SaveBlocked([for (final b in blockers) b.message])` when it
  is non-empty, before any write. Rules (design §8.6 and the ticket; confirm messages and any
  extra rule against the editors): empty display name or export key (after trim) for all three;
  item: empty `itemCategoryId` or `rarityId` (both `NOT NULL` foreign keys); recipe: empty
  `outputItemId`, `outputQuantity` below 1, an ingredient quantity below 1, duplicate ingredient
  item ids, the output item also an ingredient (use 0.1.6's `assertOutputIsNotIngredient` message
  verbatim); loot table: an entry `weight` below 1, `quantityMin` below 1, `quantityMax` below
  `quantityMin`, with field paths like `entries[2].quantityMax`. 0.1.6 silently clamped loot
  values in `setEntries`; 0.2.0 refuses instead (ticket AC), so the repository does NOT clamp.
  Broken references (an item id that no longer exists) are NOT blockers; they surface as a
  validation issue, and a foreign-key failure in SQLite would arrive as `SaveFailed`.
- Loot entry rows get a new id on every save (as 0.1.6); `conditional_flags` is stored as JSON
  text via `jsonEncode` of the draft map (insertion order, as `JSON.stringify` kept it) and read
  back with `jsonDecode`; `{}` round-trips as an empty map.
- Item custom field values: `load` reads the item's `custom_field_values` rows into the map;
  `save` writes them the way 0.1.6's `setCustomFieldValues` did (check whether it deleted all rows
  for the item first and whether null/empty values were stored or skipped, and match the stored
  result); only values for definitions scoped to the item's category are meaningful, but do not
  filter silently: match 0.1.6.
- Duplicate uses `copyDisplayName` / `copyExportKey` for all three domains (design §7). 0.1.6's
  loot table duplicate used a plain slug with no UUID suffix; 0.2.0 adds the suffix everywhere.
  Record this as a known deviation in your report. Duplicate copies ingredients, entries (new
  ids) and the item's custom field values, as the Electron methods did.
