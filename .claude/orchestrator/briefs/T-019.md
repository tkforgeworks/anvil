## Decisions already taken (do not re-decide)
- `ExportScope` is a sealed Dart type in `lib/src/export/export_scope.dart` mirroring the
  Electron shape (full project; one domain; a record selection within one domain). The context is
  a plain `Map<String, Object?>` (the presets already take it) so the fixtures compare directly.
- `assembleExportContext(ReadScope tx, ExportScope scope)` in
  `lib/src/export/context_assembler.dart` is a pure read: callers run it inside `db.read`.
- `ExportService(projectPath:)` in `lib/src/export/export_service.dart`, constructed like
  `ValidationService`. One method does what 0.1.6's preview AND execute both did, since the only
  difference was the file write, which is the app's job in 0.2.0:
  `Future<ExportOutput> render(String selectorId, ExportScope scope)`. On `Isolate.run` it opens
  its own `openReadOnly` connection, runs the gate (`validateProject`; any `error`-severity issue
  throws `ExportBlocked('Export blocked: <n> validation error(s) must be resolved before
  exporting.')`), assembles the context and renders a built-in preset in that isolate; a custom
  template is read in that isolate and rendered through the existing `renderTemplateIsolated`
  (keep its timeout and `RenderTimeout`). `ExportOutput` carries `text` (the single-file output,
  or the CSV summary), `files` (`List<CsvFile>`, empty except for CSV) and `suggestedFileName`
  (`export.json` for json presets/templates, `export.txt` otherwise, as `export.handlers.ts`
  chose). The UI isolate's connection is never used.
- `Future<List<ExportSelector>> listSelectors()` returns the three built-in presets (ids, names,
  descriptions and formats verbatim from `BUILT_IN_PRESETS`, `builtIn: true`) followed by the
  stored custom templates (`builtIn: false`) each with `TemplateCheck? unsupported` from
  `checkTemplate`, read on `Isolate.run` over a read-only connection. This is 0.1.6's
  `EXPORT_GET_TEMPLATES` plus the §11.5 status.
- `CustomTemplate` (id, name, description, templateSource, format, createdAt, updatedAt),
  `CreateTemplateInput` and `UpdateTemplateInput` (all fields optional) live in
  `lib/src/domain/custom_template.dart`. `TemplateRepository` (`list()` ordered as 0.1.6's
  `getCustomTemplates`, `get(id)`, `create(input)`, `update(id, input)`, `delete(id)`) in
  `lib/src/repositories/template_repository.dart` with `SqliteTemplateRepository`; every mutation
  is one `saveTransaction(templateChanged(name), …)` (0.1.6 wrote no history for templates; 0.2.0
  does, design §6.4); `get`, `update` and `delete` of an unknown id throw
  `RecordNotFound('custom_templates', id)`. Keep 0.1.6's timestamp behaviour as the source shows
  it (create used `new Date().toISOString()`: write that shape via
  `strftime('%Y-%m-%dT%H:%M:%fZ','now')` as `sqlite_meta_repository.dart` does; update used
  `datetime('now')`), and say so in your report.
- No dependency auto-include: in domain and selection scope the other domain arrays are empty, as
  0.1.6 (the ticket is explicit).
- Barrels: add the new public files to `lib/src/export/export.dart`, `lib/src/repositories/
  repositories.dart` and `lib/src/domain/domain.dart`, one `export` line each, lists kept sorted.
  `lib/anvil_core.dart` already exports those barrels; do not edit it.
