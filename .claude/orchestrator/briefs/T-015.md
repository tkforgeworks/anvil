## Expected outcome
### `MetaRepository` (`abstract interface class`, all `Future`s, no `sqlite3` types)
- Lists: `listStats()`, `listRarities()`, `listItemCategories()`, `listNpcTypes()`,
  `listCraftingStations()`, `listCraftingSpecializations()`, `listDerivedStats()`, each ordered as
  the Electron `META_LIST_*` handler orders (check: `sort_order` then name).
- Per list: `addX(input)`, `updateX(id, input)`, `deleteX(id)`, `reorderX(List<String> ids)`
  with the exact Electron semantics (add appends with `MAX(sort_order)+1`; update refuses an
  unknown id with `RecordNotFound('<table>', id)`; delete calls the in-use check first and throws
  `MetaInUse(kind.value, counts)` when in use, else deletes; reorder assigns `sort_order = index`
  in the given order inside one transaction). Inputs are the ANVL-174 input types (`MetaItemInput`
  for the four display-name+export-key lists and stats, `MetaRarityInput`, `DerivedStatInput`).
  Each mutation runs in `saveTransaction` with the history description 0.1.6 would have produced
  via the change accumulator for a meta change: use `projectSettingsChanged` (`Project settings
  changed`) for all seven lists; that is what the dashboard showed for meta edits.
- `Future<MetaInUseResult> checkInUse(MetaInUseKind kind, String id)` where `MetaInUseResult`
  has `bool inUse` and `String? reason` with the 0.1.6 reason strings verbatim (`Stat is used by
  3 class(es) in stat growth definitions.`, `Rarity is used by 2 item(s).`, `Item category is
  used by 1 item(s).`, `Item category has 2 custom field definition(s). Delete those fields
  first.`, the NPC type pair, `Station is used by 1 recipe(s).`, `Specialization is used by 1
  recipe(s).`, `Derived stat has overrides in 1 class(es).`). The `counts` map in `MetaInUse`
  carries the same numbers keyed `classes`, `items`, `customFieldDefinitions`, `npcs`, `recipes`
  as applicable (only the non-zero key that caused the refusal).
- `Future<ProjectSettingsDraft> loadProjectSettings()`: the three `project_info` scalars plus the
  five lists as row drafts in sort order.
- `Future<ProjectSettingsDraft> saveProjectSettings(ProjectSettingsDraft draft)`: ONE
  `saveTransaction(projectSettingsChanged, …)` that updates the three scalars, then for each of
  the five lists: inserts rows whose id starts with `newMetaIdPrefix` (assigning a fresh UUID),
  updates rows whose id exists, deletes rows present in the table but absent from the draft (after
  the in-use check; a refusal throws `MetaInUse` and the whole save rolls back), then sets
  `sort_order = index` for every surviving row in draft order. Returns `loadProjectSettings()`
  read back inside or right after the transaction. Item categories and NPC types are NOT part of
  the draft (the Custom Fields tab persists them immediately through `addX`/`updateX`/…).
### `CustomFieldRepository`

  `valueCount(id)`, `usedEnumValues(id)`. Define `UpdateCustomFieldDefinitionInput` in the

  option removal refused when any stored value uses the option, thrown as `SaveBlocked(['Cannot
  remove enum option(s) that are in use: a, b'])`; `deleteDefinition` removes its
  `custom_field_values` rows first (verify whether 0.1.6 did it by cascade or explicitly and
  match the visible result). Mutations run in `saveTransaction(customFieldDefinitionsChanged, …)`.
