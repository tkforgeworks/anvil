## Expected outcome
### Types (`validation_issue.dart`)
- `enum ValidationSeverity { error, warning, info }` and `enum ValidationDomain { classes,
  abilities, items, recipes, npcs, lootTables, derivedStats }`, each with a `String value` holding
  the 0.1.6 string (`'loot-tables'`, `'derived-stats'`) and a `fromValue`.
- `final class ValidationIssue` with `id`, `domain`, `recordId`, `recordDisplayName`,
  `String? field`, `severity`, `message`; `==`/`hashCode` over all fields EXCEPT `id`, a
  `toString`, and `Map<String, Object?> toJson()` using the 0.1.6 key names and string values
  (without `id`) for the parity tests. `id` is a per-run unique string (a counter is fine, e.g.
  `'v-1'`; Electron used `randomUUID()`, which no test can compare, so ids are excluded from
  equality and from the oracle).

### Project pass (`validate_project.dart`)
- `List<ValidationIssue> validateProject(ProjectDatabase db)`: runs every family inside ONE
  `db.read(...)` so all checks see one snapshot, and returns the issues in the Electron order:
  direct refs (descriptor order, broken then soft-deleted per descriptor), junction refs (check
  order, broken then soft-deleted), required custom fields, derived-stat syntax (base then
  overrides), derived-stat runtime, derived-stat cycles (base, then per class), stat growth
  formulas. Within a family, rows come in the order the Electron SQL returns them: copy each SQL
  statement from `engine.ts` as closely as `package:sqlite3` allows (same tables, joins, WHERE
  clauses, no added ORDER BY unless Electron has one), so SQLite returns the same row order.
- Every message string must be byte-identical to `engine.ts`:
  `References nonexistent <target> '<ref>'.`, `References soft-deleted <target> '<name>'.`,
  `Assignment references nonexistent <target> '<ref>'.`, `Assignment references soft-deleted
  <target> '<name>'.`, `Required field '<name>' is empty.`, `Formula syntax error: <err>`,
  `Override formula for '<name>' has syntax error: <err>`, `Formula for '<name>' failed at level
  1: <error>`, the two cycle messages (take them from `DerivedStatCycle.message` /
  `.overrideMessage`), `Stat growth formula for <stat>: <err>`, `Stat growth formula for <stat>
  references unknown variable(s): <a, b>. Only "level" and "max_level" are available.`, `Stat
  growth formula for <stat> fails at level <n>: <error>`. Fields: `itemCategoryId`, `rarityId`,
  `outputItemId`, `craftingStationId`, `craftingSpecializationId`, `npcTypeId`, `lootTableId`,
  `abilityAssignments`, `ingredients`, `classAssignments`, `entries`, `custom:<field_name>`,
  `formula`, `derivedStat:<name>`, `derivedStatOverrides`, `statGrowthFormula:<stat_name>`.
- Soft-delete reference severity: `project_info.soft_delete_reference_severity == 'Error'` →
  error, anything else → warning (exactly Electron's `getSoftDeleteRefSeverity`).
- Level-1 bindings exactly as `buildClassLevel1Bindings`: every stat's `export_key` →
  `COALESCE(level-1 growth value, 0)`, then class metadata fields `field_key` → `value`
  (overwriting), then `resource_multiplier`. Runtime issues only when `error != null &&
  !isSyntaxError`. Skip pairs whose effective formula failed the syntax check, as Electron does.
- Cycles: build `DerivedStatFormula` rows from `derived_stat_definitions`, call
  `findDerivedStatCycle` for the base graph (one issue per stat in the cycle, domain
  `derived-stats`, field `formula`), then per active class that has overrides with
  `overrides: {derivedStatId: formula}`; emit the per-class issue (domain `classes`, field
  `derivedStatOverrides`) only when the cycle is not `isSameCycleAs(baseCycle)`. Check that
  `findDerivedStatCycle` already drops formulas failing syntax, as Electron does; if its
  behaviour differs from `checkDerivedStatCycles` in any case, report it, do not patch it.
- Stat growth: `max_level` from `project_info`; for each formula row joined to an active class,
  syntax error → one error and `continue`; unknown variables (anything but `level`,
  `max_level`) → one warning; then evaluate levels 1..max_level with bindings `{level,
  max_level}` and report the FIRST failing level only.

### Record pass (`validate_record.dart`)
- `List<ValidationIssue> validateRecord(ProjectDatabase db, ValidationDomain domain, String id)`
  returns exactly the issues `validateProject` would produce with `recordId == id && domain ==
  domain`, in the same relative order, but computed with the record filter pushed into the SQL
  (`AND f.id = ?` / `AND o.id = ?` / `AND c.id = ?` etc.), not by running the whole project pass
  and filtering. Note the cross-record cases: a class's `derivedStatOverrides` cycle issue needs
  the base cycle computed (to apply `isSameCycleAs`), so the base graph is still read; a
  `derived-stats` record's cycle issue is one entry of the base cycle. Share the family code
  between the two passes via an optional record filter parameter rather than duplicating SQL.

### Service (`validation_service.dart`)
- `final class ValidationService { ValidationService({required String projectPath}); Future<List<ValidationIssue>> runProject(); }`
  where `runProject` uses `Isolate.run(() { final db = ProjectDatabase.openReadOnly(path); try {
  return validateProject(db); } finally { db.close(); } })`. Only the path string crosses the
  isolate boundary; the result list is plain Dart values. `ProjectDatabase.openReadOnly` already
  sets `foreign_keys = ON`. Note the fixture is in rollback-journal mode, not WAL; a read-only
