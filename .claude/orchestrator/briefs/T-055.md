# T-055: Linux packages for the 0.2.0 release (ANVL-168, Anvil side)

You are a subagent dispatched by an orchestrator. Do exactly this task, then report in the format
at the end. If blocked, stop and report.

## Goal
`scripts/release/build-linux.sh` builds the Flutter Linux release bundle and packages it as an
AppImage, a deb and an rpm in `release/`, so the org release workflow can attach them to the same
GitHub release as the Windows installer. A deb or rpm upgrade from the Electron 0.1.6 package must
replace the old install cleanly, with no duplicate menu entry and no leftover files.

## Why
0.1.x shipped `Anvil-0.1.6.AppImage`, `anvil_0.1.6_amd64.deb` and `anvil-0.1.6.x86_64.rpm` from
electron-builder. 0.2.0 is Flutter, which produces only a bundle directory, so Anvil has to package
it itself. Tim decided 2026-11-03: the org `release-flutter.yml` gets a `build-linux` input (the
orchestrator is writing that change in `tkforgeworks/.github`), and Anvil ships all three formats.

## Decisions already taken
- **Tools:** `nfpm` for deb and rpm from one `linux/packaging/nfpm.yaml`, and `appimagetool` for
  the AppImage. Both downloaded by the script at **pinned versions with sha256 checks** into a
  cache directory under `build/` (not into the repo), x86_64 only. AppImage tools run with
  `APPIMAGE_EXTRACT_AND_RUN=1` so no FUSE is needed on the runner. No `flutter_distributor`, no fpm
  (Ruby).
- **Package metadata:** name `anvil` (same as 0.1.6, so dnf/apt treat 0.2.0 as an upgrade),
  maintainer `TK ForgeWorks <tim.klimpel@gmail.com>` (0.1.6 used `TKForgeWorks <…>`), license
  `Apache-2.0`, homepage `https://github.com/tkforgeworks/anvil`, a one-line description.
  **Package version:** `X.Y.Z` for stable; for an RC, `X.Y.Z~rc.N` in both deb and rpm metadata so
  `0.2.0~rc.1 < 0.2.0` sorts correctly (rpm supports `~`). Prove the ordering in a container
  (`dpkg --compare-versions`, `rpmdev-vercmp` or `rpm --eval '%{lua:…}'`).
- **Layout:** the bundle under `/opt/Anvil/` as 0.1.6 had it, `/usr/bin/anvil` pointing at
  `/opt/Anvil/anvil`, icons in `/usr/share/icons/hicolor/<size>/apps/`. Desktop file
  `com.tkforgeworks.anvil.desktop` (the GTK app id, so GNOME Wayland matches the window to its
  launcher) with `Icon=com.tkforgeworks.anvil`, `StartupWMClass=com.tkforgeworks.anvil`,
  `Categories=Utility;` (0.1.6's category), `Exec=anvil %U`. The old `anvil.desktop` disappears
  with the old package. If testing shows the window does not report `com.tkforgeworks.anvil`
  as its WM class or app id, report that rather than renaming.
- **Runtime dependencies:** run `ldd` (or `readelf -d`) over the bundle's binary and `lib/*.so`
  and declare only what the system must provide (GTK 3 and friends; SQLite is bundled by the
  `sqlite3` build hooks, verify). Debian 13 renamed some libraries with a `t64` suffix; use
  alternatives (`libgtk-3-0t64 | libgtk-3-0`) where needed.
- **Upgrade safety:** electron-builder's maintainer scripts may remove `/usr/bin/anvil` or run
  `update-alternatives` in the old package's postrm/postun, which runs after the new package
  unpacks. Design the new package's scripts so the 0.1.6 → 0.2.0 upgrade leaves a working
  `/usr/bin/anvil` on both deb and rpm, and prove it (below).
- **AppImage:** AppDir with `AppRun` (exec the bundle's `anvil` relative to `$APPDIR`), the
  desktop file and icon at the AppDir root. It relies on the host's GTK 3, which every desktop
  distro has; do not bundle GTK.
- Write `linux/packaging/` files (nfpm config, desktop file, any maintainer scripts, AppRun) as
  source files in the repo, not heredocs inside the script, so they are reviewable.
