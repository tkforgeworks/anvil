## Decisions to record (authoritative)

### D1. Product constraints carried over
Same repo, rewrite on `v0.2.0/main`; same `.anvil` SQLite project files (schema and the 7 migrations kept, files created by 0.1.x open unchanged); Windows + Linux only; Electron source stays as reference until cutover; 0.1.6 final Electron release.

### D2. Project layout and the core/UI boundary
- Pub workspace at the repo root. Flutter app `anvil` at root: `lib/main.dart`, `lib/app/` (shell, theme, routing, settings UI, menu/shortcuts), `lib/features/<area>/` (one folder per domain editor/list: classes, abilities, items, recipes, npcs, loot_tables; plus dashboard, validation, recycle_bin, export, project). App-side Riverpod providers live beside the feature they serve, with the root overrides in `lib/app/providers.dart`.
- `packages/anvil_core` (pure Dart, never imports `package:flutter`, no Riverpod either): `lib/src/db/` (ProjectDatabase, pragmas, migration runner + the 7 migrations as Dart files holding SQL strings), `lib/src/domain/` (record and draft types per domain, meta types, custom field types, settings types), `lib/src/repositories/` (abstract interfaces + `sqlite_*` implementations), `lib/src/project/` (project lifecycle: create/open/close/lock/recent/folder structure/save history/backup), `lib/src/formula/`, `lib/src/validation/`, `lib/src/export/` (js_compat, presets, template renderer, context assembler), `lib/src/settings/` (app settings model + custom theme parser — already exists), `lib/src/logging/`. Public API through `lib/anvil_core.dart` only.
- Rule: the app depends on the core, never the reverse; everything in the core runs under `dart test`. `DraftHistory<T>` (undo) lives in the core; the `AsyncNotifier`s that hold drafts live in the app.
- Explain what replaces the Electron main/renderer split: there is one process; the "main process" responsibilities (DB, files, formula, export, validation, migrations, lock) become the core package called directly from the app; isolation where needed is by isolate, not process.

### D3. SQLite access: `package:sqlite3` 3.x, raw SQL, no ORM
- Choice: `sqlite3` ^3.8 (pub.dev 3.8.0, 2026-10) with its native build hooks bundling SQLite on Linux and Windows (no system libsqlite3, no `sqlite3_flutter_libs`, which is end-of-life). Raw SQL, prepared statements, no ORM.
- Criteria and how each candidate scores (table): (a) one-for-one port of the 7 migrations — sqlite3: SQL strings copied verbatim; Drift: possible via `customStatement` but fights its schema model; (b) existing `.anvil` files open unchanged — both can, but Drift's generated schema would have to be reverse-engineered to match and its `schemaVersion`/`MigrationStrategy` duplicates the `schema_migrations` table Electron already keeps; (c) testable without Flutter — both run in pure Dart (`NativeDatabase` for Drift), sqlite3 with no codegen; (d) cloud path — neither avoids SQLite; the lock-in is controlled by the repository boundary (D4) and by keeping the file self-contained, so Drift's typed queries buy nothing on that axis; (e) toolchain weight — Drift needs `build_runner`/`drift_dev` codegen in every core change, sqlite3 none; (f) org precedent — Cheesy Scribe uses Drift for a greenfield schema it owns; Anvil's schema is inherited and must stay byte-compatible, so the precedent does not transfer. Record Drift as considered and rejected with these reasons, and name the one situation that would reopen it (a greenfield schema or a sync layer that wants Drift's stream queries).
- Pragmas on open as Electron: `journal_mode = WAL`, `foreign_keys = ON`. Copies/backups via the SQLite backup API or `VACUUM INTO`, never `File.copy` of an open WAL database (158 finding 9). `sqlite3` is synchronous; repository methods still return `Future`s so a background isolate or remote backend later does not change editor code (158 finding 11).
- Migration compatibility contract: `schema_migrations(filename, applied_at)` with the same 7 filenames (`001_init` … `007_save_history`), `CURRENT_SCHEMA_VERSION = 7`, `project_info.schema_version` updated the same way, non-destructive upgrade (copy the original before applying, as Electron does). Compatibility tests: (1) `fixtures/sample-0.1.6.anvil` (Electron-generated, in `~/projects/anvil-spike-fixtures`, to be checked into `packages/anvil_core/test/fixtures/` with its generator) opens with zero pending migrations and its rows read back; (2) a fresh project created by the Dart runner has an identical `sqlite_master` (normalised SQL) to the Electron-created fixture; (3) each migration applied to the previous fixture state matches.

### D4. Repository boundary
- One `abstract interface class` per domain in the core (`ClassRepository`, `AbilityRepository`, `ItemRepository`, `RecipeRepository`, `NpcRepository`, `LootTableRepository`), plus `MetaRepository` (stats, rarities, categories, NPC types, stations, specializations, derived stat definitions, project settings), `CustomFieldRepository`, `TemplateRepository` (custom templates), `SaveHistoryRepository`, `LifecycleRepository` (cross-domain bulk soft-delete/restore/hard-delete/empty trash/impact). Methods return `Future`s, take and return domain types and drafts; no SQL, no `sqlite3` types cross the boundary. Derive the method inventory from the Electron repositories + IPC channel groups (summarise as a table per interface: list/get/create/save(draft)/softDelete/restore/hardDelete/duplicate/getUsedBy/… and the domain-specific ones like stat growth, formulas, assignments, entries).
- `Sqlite*Repository` implementations in the core share a `ProjectDatabase` that owns the handle privately and exposes `saveTransaction(description, body)` (BEGIN IMMEDIATE … COMMIT, save_history insert + trim to 50, ROLLBACK on error guarded by `!autocommit`), per 158 recommendation 4.
- Editors and the draft layer (ANVL-159) depend on the interfaces only, obtained from root-overridden providers. A cloud backend, backup hook or sync layer wraps or replaces the implementation without touching editors.

### D5. State management and the save model (decided in ANVL-157/158)
- Riverpod 3 (`flutter_riverpod` ^3.4) without codegen; hand-written providers.
- One immutable `XDraft` per domain with value equality (hand-written `==`/`hashCode` + test), holding editable fields and each junction list as an ordered list (sort_order = index); baseline = record as read back inside the save transaction; `isDirty = draft != baseline`.
- `DraftHistory<T>` in the core: 500 ms coalescing for same-field edits, structural edits one step, edit-back-to-previous counts as undo, cap 200, baseline moves on save and stack kept.
- Editor state: `AsyncNotifierProvider.autoDispose.family<XEditorController, XEditorState, String>` keyed by record id; intent methods (`setDisplayName`, `addIngredient`, `undo`, `save`); `build()` watches only stable providers (project, repository), reads volatile settings at call time (158 gotcha 6); retries disabled in tests.
- Record-level save replaces project-level save/dirty/auto-save (ANVL-163): each record save is one transaction with one save_history row; the Electron change accumulator and tiered descriptions are dropped; save status shown in the shell; "checkpoint quietly" (WAL checkpoint) on idle/close. State what `is_auto_save` means now (keep the column; write 0 for user saves; note the decision point).
- Validation at save: blocking rules run in the notifier and again inside the repository save (ANVL-164).
- Keyboard layering (158 rec 3): framework `DefaultTextEditingShortcuts` own text keys in fields; app-shell `Shortcuts` holds app-level intents (ported ANVL-113 registry) and never binds `UndoTextIntent`/`RedoTextIntent`; each editor has a `RecordEditorShortcuts` layer around an autofocus `FocusScope` with `SaveRecordIntent` (Ctrl+S) and `UndoDraftIntent`/`RedoDraftIntent` (Ctrl+Z, Ctrl+Shift+Z, Ctrl+Y) disabled while an `EditableText` has focus; dialogs are separate routes; avoid `DropdownMenu` where undo matters (it contains an `EditableText`), prefer `DropdownButton`/menu anchors.
- Leave guard via `PopScope(canPop: !isDirty)` (ANVL-161). List actions (soft delete etc.) are instant with an Undo snackbar (ANVL-166).

### D6. Export engine (decided in ANVL-151)
Record all nine points of FINDINGS §8 verbatim in substance: purpose-built renderer of a Nunjucks-compatible subset in `anvil_core/lib/src/export/`, rejected options (jinja.dart, embedded JS runtime) with reasons; byte-for-byte compatibility contract with the parity corpus and fixtures as the spec (oracle regenerated against Electron `node_modules` until cutover, then frozen); JS value semantics as part of the contract; REAL→double number rule; sandbox model (no host calls, `RenderLimits` defaults: 5,000,000 iterations, 32 M chars per string, 256 M chars total string work, nesting 200; render off the UI isolate; templates in project files are untrusted input); unsupported-template policy (check on load, warn per template with line/column, disable in selector, never rewrite); kept quirks (`export_key` not resolving meta ids, flat JSON `derived_stat_export_key` raw id, CSV `\r` handling); the 0.1.6 template escape as a known issue the rewrite closes; presets are Dart code, not templates. Context assembler ported to the core; file write through the app's save dialog defaulting to the project `exports/` folder; export gate on validation errors kept.

### D7. Formula engine
- Port `src/main/formula/engine.ts` (recursive-descent parser/evaluator, `FormulaSyntaxError`/`FormulaRuntimeError`, `evaluateFormula`, `validateFormula`, `extractVariableNames`) to `anvil_core/lib/src/formula/` as pure Dart with the same grammar and error messages (write a parity test against the Electron engine's cases).
- Where it runs now: in-process. Single evaluations are microseconds and run synchronously in the notifier. Batch evaluation (stat growth formulas across all levels for all stats, derived-stat previews, the validation pass) is debounced in the notifier (300 ms as the Electron stat-growth editor did) and, when a batch exceeds a threshold (state one, e.g. 2,000 evaluations), runs via `Isolate.run` on a snapshot of the inputs. Results are cached per (formula, bindings) in the notifier for the editor session. Cycle detection for derived stats kept as in the validation engine.

### D8. Validation
Port `validateProject` and its check families (broken/soft-deleted references across FKs and junctions, required custom fields, derived-stat formula syntax/runtime/cycle with per-class overrides, stat-growth formulas across levels) to `anvil_core/lib/src/validation/`, running against the repository/database layer. Project-wide validation runs on a background isolate that opens its own read connection to the same file (WAL allows concurrent readers; sqlite3 handles are not sendable); record-level validation runs in-process at save. Severity settings (soft-delete reference severity) kept in project settings. Inline display + global panel + sidebar badge kept (ANVL-148/149 scope).

### D9. Project lifecycle
Create/open/close with the `{ProjectName}/database/exports/temp/logs/` folder structure and `defaultSaveLocation`; `.anvil.lock` sidecar lock file written with `wx` semantics holding pid/lockedAt (same format as Electron so a 0.1.6 instance and 0.2.0 respect each other's lock); recent projects list (10) in the app support directory (`path_provider` getApplicationSupportDirectory); non-destructive migration on open with a copy; recovery-mode message on integrity failure; backup via backup API/`VACUUM INTO` to a user-chosen path; save history (migration 007) kept and written per record save; weekly deltas and auto-save info dashboard tiles: deltas kept, the auto-save countdown dropped with project-level auto-save.

### D10. Application shell and UI stack
- `forge_ui` (git dependency pinned to a tag) for theme, tokens, fonts and shared widgets; app theme in `lib/app/theme/` as built by ANVL-154 (dark/light/custom-file modes, Electron palette parity); no colour literals outside the two allowed files (test-enforced). Status colour roles move to `forge_ui` when FU-9..12 ship (ANVL-170).
- Navigation: `go_router` (^18) with a shell route for the sidebar + title area and routes per list/editor/utility page; the Electron "editing mode" setting (modal vs full-page) is kept: the editor widget is the same, shown either as a route or in a dialog.
- Window: native OS frame in 0.2.0 (the Electron frameless custom title bar is dropped; fewer moving parts and no `window_manager` dependency, which is mid-migration upstream); minimum window size 900×600 set from the runner (`linux/my_application.cc` / `windows/runner/main.cpp`) rather than a plugin. Save status and project name go in the app bar.
- Menu + shortcuts: the ANVL-113 hamburger menu rebuilt with `MenuAnchor`/`MenuItemButton`, the shortcut registry as `Shortcuts`/`Actions` intents (never `UndoTextIntent`), a shortcuts cheatsheet dialog; settings as dialogs (app settings, project settings with buffered meta lists per ANVL-121).
- Charts: `fl_chart` (^1.3) replaces Recharts for stat growth and loot weight visualisation.
- Lists: `DataTable`/custom rows with multi-select, bulk actions, Active/Archived toggle; recycle bin page; context menus (ANVL-117).
- Telemetry (build-time gated) is dropped for 0.2.0 unless re-ticketed; file logging kept (D11).

### D11. Settings and logging
App settings JSON in the application support directory (same keys as `AppSettings`: auto-save interval becomes unused — note it; default save location; custom theme path; custom theme colors; editing mode); custom theme parser already in the core. File logger `anvil-YYYY-MM-DD.log` with size rotation (5 MB, 3 backups) in `<support dir>/logs/`, `FlutterError.onError` and `PlatformDispatcher.onError` → log; `runZonedGuarded` for the app.

### D13. Testing strategy
Core: `dart test` in `packages/anvil_core`, fixture copies per test (`FixtureCopy`), parity tests against Electron outputs (schema diff, export bytes, formula cases), migration tests. App: widget tests under `TargetPlatformVariant.only(TargetPlatform.linux)` for keyboard routing, `no_hardcoded_colors_test`, theme parity tests; no golden tests for the app (forge_ui owns the look). CI: `ci / ci` (root) + `core / ci` via org `ci-flutter.yml`, both required on `main`. Memory note: cap concurrency on heavy test runs.

### D14. Future cloud (notes, not 0.2.0 scope)
Cloud backup: upload the whole `.anvil` produced by `VACUUM INTO` (consistent snapshot) to Supabase Storage through `forge-core` (sign-in, session) from a `BackupService` that depends only on `ProjectDatabase.snapshot(path)` and a `BackupTarget` interface; restore = download + open. Record-level sync or a mobile client would additionally need: globally unique record ids (domain ids are already UUIDs — check the migrations and say which tables use UUID vs autoincrement), change timestamps (`updated_at` exists; a per-row `revision`/change log table would be a new migration), a conflict policy (last-writer-wins per record with the draft baseline check from D5 as the local half), sign-in via `forge-core`, and a `RemoteXRepository` or a sync layer wrapping `Sqlite*Repository` emitting change records after COMMIT. None of this changes editors because of D4.
