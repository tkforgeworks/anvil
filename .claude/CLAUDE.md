# Anvil — Claude Code Project Instructions

## Project Overview

Anvil is a desktop RPG data management tool built with Electron + React + TypeScript + SQLite. It provides structured editors for six first-class game data domains (Character Classes, Abilities, Items, Crafting Recipes, NPCs, Loot Tables) and a Nunjucks-based export engine.

## Direction: Flutter rewrite (0.2.0)

Decided 2026-10-11. **0.1.6 is the final Electron release** (shipped 2026-10-11). Anvil is being rebuilt in Flutter and released as 0.2.0. Do not start new Electron feature work — route new work to the rewrite epics.

- **Same repo.** The rewrite accumulates on `v0.2.0/main`, cut from `main` on 2026-10-31 after 0.1.6 shipped. The Electron source stays in place as the porting reference until cutover (ANVL-169).
- **Layout (ANVL-152).** The Flutter app lives at the repo root (`lib/`, `test/`, `linux/`, `windows/`, `pubspec.yaml`); it does not collide with the Electron `src/` and `package.json`. The Flutter-free core is the pub-workspace package `packages/anvil_core`, which must never depend on `package:flutter` — its pubspec has no Flutter dependency, so any such import fails analysis. Toolchain: `.fvmrc` pins Flutter 3.47.5 (`fvm use 3.47.5`, then `fvm flutter ...`). Checks from the root: `dart format --set-exit-if-changed .`, `flutter analyze`, and `flutter test test packages/anvil_core/test` — a bare `flutter test` runs only the app's `test/`, not the workspace member's, so the core path must be passed (or `dart test` run inside `packages/anvil_core`); ANVL-153 has to account for this in CI.
- **Same SQLite project files.** Schema and migrations are kept so projects created in the Electron app open unchanged.
- **Windows + Linux only.**
- **Jira:** fix version `0.2.0`, label `flutter-rewrite`. Epics: ANVL-146 (foundation and architecture), ANVL-147 (data and domain core), ANVL-148 (application shell and shared UI), ANVL-149 (domain editors), ANVL-150 (release and cutover).
- **Design:** `design_notes/Anvil_Implementation_Design_v2_0.md` (ANVL-155) is the architecture of the rewrite; the "Architecture Decisions" section below is its summary. Sections of this file that still describe the Electron app (Domain Model, CI & Release, Known Technical Debt, Phase Plan) say so where it matters and are replaced at cutover (ANVL-169).

## Architecture Decisions (Do Not Reverse Without Discussion)

Decided for the Flutter rewrite by ANVL-155 (2026-10-31) and recorded in `design_notes/Anvil_Implementation_Design_v2_0.md`, which has the reasons. The rewrite itself was the discussion that revised the Electron-era list (decided 2026-10-11). Raise a question before deviating from any of them.

**Electron-era decisions, status for the Flutter line:**

| Electron decision | Status | Flutter rule |
| :---- | :---- | :---- |
| Main/renderer strict split; all data through typed IPC via `contextBridge` | **Dropped** | One process. The Flutter-free core package `packages/anvil_core` takes over every main-process responsibility (database, files, migrations, lock, formula, validation, export) and the app calls it directly. Isolation where needed is by isolate, not by process. The `domain:operation` IPC convention becomes methods on repository interfaces. |
| SQLite via `better-sqlite3`, raw SQL, no ORM | **Revised** | SQLite via `package:sqlite3` 3.x (native build hooks bundle SQLite on Linux and Windows; no system library, no end-of-life `sqlite3_flutter_libs`), raw SQL, no ORM. Drift was weighed and rejected: Anvil's schema is inherited and must stay byte-compatible, codegen buys nothing on the cloud axis, and the repository boundary controls the lock-in. Pragmas as Electron: `journal_mode = WAL`, `foreign_keys = ON`. Copies and backups use the backup API or `VACUUM INTO`, never a file copy of an open WAL database. |
| Three-part record identity (internal id, display name, export key) | **Kept** | Unchanged. The three fields are never conflated. |
| Soft-delete by default; hard delete only from archive views and the recycle bin | **Kept** | Unchanged. |
| Custom fields are scalar/enum only (`text`, `integer`, `decimal`, `boolean`, `enum`) | **Kept** | Unchanged; no cross-domain reference field types. |
| Formula engine runs in the main process, debounced and cached | **Revised** | The engine is ported to `anvil_core` as pure Dart with the same grammar and messages and runs in-process. Single evaluations are synchronous in the editor notifier; batches (stat growth across levels, derived-stat previews, validation) are debounced in the notifier and run via `Isolate.run` above a threshold; results are cached per formula and bindings for the editor session. |
| Loot table drop weights are integers | **Kept** | Unchanged. |
| Abilities and Loot Tables are first-class domains | **Kept** | Unchanged; own tables, repositories, list views and editors. |
| Export presets are Nested JSON, Flat JSON and CSV | **Kept** | Unchanged, ported as Dart code (they were never templates) and byte-identical to 0.1.6 output. |
| Nunjucks for export templates, "sandboxed" in the main process | **Revised** | A purpose-built Dart renderer of a Nunjucks-compatible subset in `anvil_core`, safe by construction (no host calls, includes, macros or recursion; render limits; rendering off the UI isolate). Output is byte-identical to 0.1.6 for supported features; the ANVL-151 parity corpus and fixtures are the specification. Templates using unsupported features are detected on load, warned about with line and column, disabled in the selector and never rewritten. 0.1.6's Nunjucks is **not sandboxed** (ANVL-151): a template can run arbitrary JavaScript with Node's `process`; it is frozen as a known issue that 0.2.0 closes. |

**New decisions for the Flutter line:**

- **Core/UI boundary.** `packages/anvil_core` never imports `package:flutter` (or Riverpod); its pubspec has no Flutter dependency, so any such import fails analysis, and everything in it runs under `dart test`. The app depends on the core, never the reverse. `DraftHistory<T>` (undo) lives in the core; the notifiers that hold drafts live in the app.
- **Repository boundary.** One `abstract interface class` per domain in the core (plus meta, custom fields, templates, save history and cross-domain lifecycle), returning `Future`s and taking domain types and drafts. No SQL and no `sqlite3` types cross it. `Sqlite*Repository` implementations share a `ProjectDatabase` that owns the handle privately and exposes `saveTransaction(description, body)`. Editors and the draft layer depend on the interfaces only, through root-overridden providers, so a cloud backend, backup hook or sync layer wraps the implementation without touching editors.
- **Migration compatibility contract.** The `schema_migrations(filename, applied_at)` table and the seven filenames `001_init` to `007_save_history` are kept verbatim, `CURRENT_SCHEMA_VERSION = 7`, `project_info.schema_version` is updated the same way, and upgrades copy the original first. Compatibility is proven by tests against the Electron-generated 0.1.6 fixture: it opens with no pending migrations, and a fresh Dart-created project has an identical normalised `sqlite_master`.
- **State management and save model** (ANVL-157): Riverpod 3 without codegen; one immutable value-equal draft per editor keyed by record id in an `AsyncNotifier` family; record-level save in one transaction with one `save_history` row; project-level save, dirty flag, auto-save timer and the change accumulator are gone. Notifier `build()` watches only stable providers (project, repository) and reads volatile settings at call time. App-shell shortcuts never bind `UndoTextIntent`/`RedoTextIntent`; each editor has its own shortcut layer around an autofocus `FocusScope`, with draft undo/redo disabled while an `EditableText` has focus.
- **Shell stack.** `forge_ui` for theme, tokens, fonts and shared widgets (the colour rule below); `go_router` for routing with the Electron modal/full-page editing mode kept; native OS window frame (the frameless custom title bar is dropped) with the 1400×600 minimum (the size 0.1.6 enforced) set in the platform runners; `MenuAnchor`-based hamburger menu and `Shortcuts`/`Actions` for the ANVL-113 registry; `fl_chart` replaces Recharts.
- **Project lifecycle.** The `{ProjectName}/database/exports/temp/logs/` folder structure, the `.anvil.lock` sidecar (same JSON as Electron so 0.1.6 and 0.2.0 respect each other's lock), the recent-projects list and app settings in the application support directory, non-destructive migration on open, and file logging with 5 MB rotation are all kept.
- **Future cloud** stays notes, not scope: a whole-file backup through `forge-core` attaches to the core via a snapshot (`VACUUM INTO`) and a `BackupTarget` interface; record-level sync would need change timestamps or a change log (a new migration), a conflict policy and a remote repository implementation, none of which touch editors because of the repository boundary.

## Domain Model Summary

Six first-class data domains, each with full CRUD, soft-delete, custom fields (where applicable), and export context participation:

1. **Character Classes** — stat growth curves, derived stat formulas, ability references
2. **Abilities** — reusable records assignable to both classes and NPCs
3. **Items** — categorized, rarity-tiered, with per-category custom fields
4. **Crafting Recipes** — ingredient + output item resolution, station and specialization references
5. **NPCs** — typed (per NPC type custom fields), class-based stat inheritance (additive, multi-class), loot table and ability references
6. **Loot Tables** — standalone drop tables with integer weight entries referencing items

## CI & Release Workflow

Two GitHub Actions workflows in `.github/workflows/`:

- **`ci.yml`** — triggers on pushes to non-main branches and `pull_request` to main **and** to `v*/main` release branches (the org CI trigger envelope from `tkforgeworks/.github/docs/ci-standards.md`). Since ANVL-153 (on `v0.2.0/main`) it calls the org reusable `tkforgeworks/.github/.github/workflows/ci-flutter.yml@main` (`flutter pub get`, `dart format --set-exit-if-changed`, `flutter analyze`, `flutter test`; no platform builds, those belong to the release workflow) with `flutter-version: '3.47.5'`, the same pin as `.fvmrc`. Two caller jobs, because a bare `flutter test` only runs the package it is invoked in: `ci` at the repo root and `core` with `working-directory: packages/anvil_core`. The resulting checks are `ci / ci` and `core / ci`; both are required on main. The Electron `validate` job (npm audit, typecheck, vitest, build) no longer runs on the rewrite branch; the Electron code is frozen at 0.1.6 and `main` still carries the old workflow until the 0.2.0 release PR lands. On release-branch PRs the checks report but are not required (see Branching & protection below).
- **`release.yml`** — triggers on `push` to main **and** to `v*/main` version branches (shared TK ForgeWorks tagless flow, mirrored in claude-observability-gui). Reads version from `package.json` and self-gates: skips if the `v{version}` tag already exists, skips an RC version on main (finalize on the version branch first), and skips a stable version on a version branch (the stable release is cut on merge to main). Otherwise: shared workflow generates release notes → Windows + Linux matrix builds upload workflow artifacts (telemetry compiled in only on prerelease versions) → a single `publish` job creates a draft GitHub Release with all assets and notes, then flips it to published (immutable-release safe; publishing creates the tag).

**Packaging is electron-builder 26** (config in the `build` key of `package.json`, output to `release/`). Windows ships an NSIS assisted installer (`oneClick: false` — wizard with per-user/all-users choice and install-dir selection, desktop + Start Menu shortcuts; the 512×512 `resources/icon.png` is auto-converted to `.ico`). Linux ships AppImage/deb/rpm. Electron Forge was removed — its `maker-squirrel` Setup.exe installed silently to `%LocalAppData%` with no wizard and, without Squirrel event handling, never created shortcuts. `npm run make` = `electron-vite build && electron-builder --publish never` (`--publish never` is required: electron-builder otherwise auto-publishes to GitHub Releases when it detects CI, failing on missing GH_TOKEN — release.yml does its own asset upload); `npm run package` = unpacked dir build. release.yml uploads only `release/*.{exe,AppImage,deb,rpm}`.

**Release notes are generated by the shared org standard** — `tkforgeworks/.github` hosts the canonical `scripts/generate-release-notes.js` and a `release-notes.yml` reusable workflow (`workflow_call`). Anvil consumes it with `ticket-prefix: ANVL` and an explicit `release-version` (required because anvil's push-to-main flow runs before the tag exists; tag-triggered repos like claude-observability-gui omit it). There is no local copy of the script — changes to note format belong in the standards repo, where they apply to all adopters.

**Commit subjects are the changelog contract.** Notes are built from commit subjects since the previous tag (previous *stable* tag for stable releases, so final notes span all RCs). Version-bump and merge commits are filtered out. Subjects starting with `Fix` or `ANVL-N: Fix ...` land under "Bug Fixes", everything else under "Changes"; `ANVL-N` keys become Jira links. Write commit subjects as user-readable changelog lines, prefixed with the ticket key when there is one.

**Jira project migrated (July 2026):** the Anvil Jira project is now the team-managed *Software* project with key **ANVL** (has Releases/fix versions). The old business-type ANV project was migrated out — all 137 issues were bulk-moved and renumbered (e.g. ANV-136 → ANVL-123, ANV-113 → ANVL-10); old `ANV-###` URLs redirect to the moved issues. Use `ANVL-N` keys in all new commit subjects and tickets.

**Fix-version categorization convention:** every open ticket gets a fix version at creation, chosen from three buckets:
- **Current release** (e.g. `0.1.5`) — in scope for the release cycle underway.
- **Next / future work** (e.g. `0.1.6`) — deferred items, typically identified during RC testing, that won't make the current release. When a release ships, this bucket becomes the next current release.
- **`1.0.0`** — big-picture items collected for the major release; no near-term cycle assignment.

Tickets found during an RC run are triaged into one of these rather than left unversioned. The Releases page in Jira (project ANVL) is the release-planning view.

### Release process (RC → stable)

1. Topic branches named `vX.Y.Z/anvl-N-short-topic` (e.g. `v0.1.5/anvl-141-release-branch-ci-ruleset`) are cut from and PR'd **into** the release branch (e.g. `v0.1.5/main`), never into main. Delete the topic branch after merge.
2. **Cut an RC**: `npm run rc:patch|minor|major` from the version branch — **the bump type is relative to the previous stable version, not the branch name** (a `v0.1.5/main` cycle following stable 0.1.4 needs `rc:patch`; `rc:minor` would produce `0.2.0-rc.1`). The script refuses to run on main, fetches remote tags, bumps `package.json` to the next `-rc.N` (no local git tags), commits, and pushes the version branch. **No PR is opened**: the push itself triggers `release.yml`, which publishes the `v{X.Y.Z}-rc.N` prerelease and creates the tag. Repeat 1–2 as you test and iterate; main is untouched throughout.
3. **Finalize**: once the last RC is verified, `npm run release:final` promotes the current RC to its stable version (`0.1.4-rc.2` → `0.1.4`; errors if the current version isn't an RC), pushes it to the version branch (no release fires — stable on a version branch is skipped), and opens a PR into main. Merging that PR cuts the stable release.
4. `release:patch|minor|major` are **only** for direct stable releases with no RC phase — they strip any rc suffix and bump *past* it, so never use them to finalize an RC cycle.

### Branching & protection (org standard)

Anvil follows `tkforgeworks/.github/docs/branching-and-release.md`: **main is the released state**; work accumulates on the current release branch `vX.Y.Z/main`; topic branches PR **into the release branch**, never into main; the release branch reaches main via the release PR that `npm run release:final` opens.

Two repository rulesets enforce this (standard: `tkforgeworks/.github/docs/branch-protection-ruleset.md`; rulesets, not classic branch protection):

- **`main`** (ruleset id 16447467) — PR-only, no force-push or deletion, **no bypass actors** (not even admins). Required checks: `ci / ci` and `core / ci` (GitHub Actions), switched from the Electron `validate` by `PUT` when ANVL-153 landed (2026-10-31) rather than at cutover, because 0.1.6 is the final Electron release and no Electron PR into main is planned; an Electron hotfix branch would carry the old workflow and report `validate`, so it would need the emergency path below. Strict up-to-date policy: the PR must contain the current main tip before merge.
- **`release-branches`** (ruleset id 22348077, added by ANVL-141) — matches `refs/heads/v*/main`; blocks force-push and deletion only. Deliberately **no PR rule and no required check**: `rc-tag.js` / `release-tag.js` push version-bump commits straight to the release branch, and a required check rejects any direct push of a new commit. A red topic-PR merged into a release branch is therefore possible; it is caught at the release PR into main. Don't add the check here — if gating is ever wanted, change the scripts to open PRs first.

Emergency changes to main require disabling the ruleset (`enforcement: "disabled"`), acting, and re-enabling — deliberate friction. **Never hand-edit the version or push tags**; CI creates the tag when it publishes.

## Known Technical Debt

**better-sqlite3 ABI — test vs. Electron binary**
`npm run rebuild` compiles `better-sqlite3` against Electron's ABI. Running `npm test` after that will fail with `NODE_MODULE_VERSION` mismatch. Fix by running `npm rebuild better-sqlite3` first, then `npm run rebuild` after tests to restore the Electron binary. See `docs/testing.md` for details.

**The audit gate does not cover the Electron runtime**
`electron` is a devDependency, so CI's `npm audit --omit=dev` never reports advisories against it even though it is the runtime every installer ships. Check it explicitly with `npm audit` (no `--omit`) before each release and keep it on the latest patch of its major. The remaining dev-only findings (`@electron/rebuild`, `electron-builder`, `vitest` chains) are build tooling and need a major `@electron/rebuild` bump to clear.

**Regenerate `package-lock.json` with npm 10**
CI runs Node 22 (npm 10). npm 11 prunes optional-peer entries (`terser`, `yaml`, `acorn`) from the lockfile, producing a noisy diff. After changing dependencies run `npx npm@10 install --package-lock-only`, then `npx npm@10 ci` to confirm the clean install CI will do.

**Frontend stack (post ANVL-119):** React 19.2, `react-router` 8 (imports from `'react-router'` — `react-router-dom` is gone; never reintroduce it or the 7.x line, which carries high-severity advisories), MUI 9, Recharts 3, `@vitejs/plugin-react` 5 (pinned to the vite 7 line that electron-vite 5 bundles; plugin-react 6 needs vite 8). MUI 9 removed the `inputProps`/`InputProps`/`*TypographyProps`/`TransitionComponent` style props (use `slotProps`/`slots`) and system props on `Stack`/`Typography` (`alignItems`, `fontWeight`, … go in `sx`). `tsconfig.main.json` uses `module: ESNext` + `moduleResolution: bundler` (typecheck only — electron-vite bundles main).

## Development Conventions

- **Constructor injection over field injection** (when applicable in any DI patterns used)
- **Explicit over magic** — avoid framework features that obscure what's actually happening
- **Vitest covers `src/main/**` and `src/renderer/**` `*.test.ts`** (`vitest.config.ts`). Renderer tests must stay free of DOM/React — keep testable logic in pure modules (e.g. `meta-buffer.ts`) and test those.
- **Tests test behavior, not implementation** — if tests are written, they should verify outcomes, not internal call sequences
- **License: Apache-2.0** (`LICENSE` is the verbatim Apache text — never edit it). Image assets (`.svg`/`.png`/`.ico`/etc.) are **all rights reserved** via `NOTICE`. `package.json` `license` must stay `Apache-2.0` (electron-builder copies it into deb/rpm metadata). Standard: `tkforgeworks/.github/docs/licensing.md`.
- **Widget colours come from the theme, never literals (Flutter, ANVL-154).** Read colours through `context.colors` (the Material `ColorScheme`), `context.forge` (`ForgeTokens`, including the warning / info / success intents and their containers since forge_ui 0.2.2) and `context.anvil` (`AnvilColors`: only the emphasised primary and disabled text), and non-colour constants through `AnvilSpacing`/`AnvilRadii`/`AnvilLayout`/`AnvilType`, so Dark, Light and Custom modes all apply. No `Color(0x…)`, `Color.fromARGB(…)` or `Colors.x` (other than `Colors.transparent`) outside `lib/app/theme/anvil_palette.dart` (the Electron palette) and `lib/app/theme/color_math.dart` (colours built from parsed theme-file channels); `test/theme/no_hardcoded_colors_test.dart` fails the build on any other literal in `lib/`. A colour role or component Anvil needs that `forge_ui` lacks is raised as a `forge-ui` ticket, not patched locally (ANVL-170 removed the last such workarounds once forge_ui 0.2.2 shipped); Anvil-only roles go in `AnvilColors`. The theme is built at `ForgeDensity.desktop`, so buttons size to their label and the scrollbar is forge_ui's; the app sets no scrollbar or density of its own. Fonts come from `forge_ui`'s bundled Poppins / JetBrains Mono / Source Serif 4 (`ForgeType`, `ForgeType.code` for code and export keys, `AnvilType.numeric` for tabular figures); the app declares no fonts and never adds `google_fonts`. (The Electron rule this replaces: renderer colours came from the MUI theme via palette tokens or `alpha(theme.palette.x, n)`, never hex/rgba literals.)
- **IPC channels follow the pattern `domain:operation`** (Electron only) — e.g., `classes:list`, `abilities:create`, `loot-tables:get`. In the Flutter app the same operations are methods on the repository interfaces in `anvil_core`; there is no IPC.
- **Flutter tests (ANVL-155, ANVL-171).** Core logic is tested with `dart test` in `packages/anvil_core` (also run by `fvm flutter test test packages/anvil_core/test` from the root), opening a fresh copy of a real fixture per test through `FixtureCopy` in `packages/anvil_core/test/db/support/fixture_copy.dart`, whose `tearDown` asserts the fixture bytes are unchanged; parity with Electron (schema, export bytes, formula cases) is asserted against the checked-in 0.1.6 fixtures in `packages/anvil_core/test/fixtures/` (see its README; never regenerate `sample-0.1.6.anvil`, the ids and timestamps would change; the per-step schema dumps can be regenerated from the Electron tree with the documented `-t` filter). App widget tests that touch keyboard routing run under `TargetPlatformVariant.only(TargetPlatform.linux)`. The app has no golden tests; `forge_ui` owns the look.
- **Migrations are sequential and non-destructive** — each migration file has a version number; upgrading a project file creates a copy of the original before applying changes. In the Flutter core the seven Electron migrations are ported as Dart files holding the same SQL and the same `schema_migrations` filenames; a new migration is `008_…` in both the filename and the Dart file.
- **No half-finished commits** — each commit must leave the codebase in a working state
